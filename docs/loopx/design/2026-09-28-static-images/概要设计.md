## 模块与数据边界

<a id="D-001"></a>
**D-001 · 架构合同**：新增 `apps/images` React/TypeScript/Vite 应用，入口 `/images/`，独立依赖与测试。复用根构建的暂存发布机制、全站颜色变量与主题控制器，不依赖跑步业务。初版图片固定存入独立 GitHub 仓库 `hugh-zhan9/hugh-image` 的 `main` 分支（当前已扩展为 D-006 仓库池），浏览器直接调用 GitHub REST API。无服务器和数据库。

```text
当前仓库 ──组合构建──> 静态站点 /images/
                          │ 下载页面
                       用户浏览器 ──用户输入的 Token──> GitHub API
                          │                              │ 只创建
                          └──读取公开图片外链────────> 独立图片仓库
```

现有复用点：`scripts/build.mjs`、`assets/css/site-tokens.css`、`static/js/themetoggle.js`。兰空的 Blade 模板耦合 PHP 路由、用户组和数据库，且未提供 Git 存储驱动；只借鉴操作流程，不复制源码。保留 Hugo、跑步路由及数据合同；新增构建失败时保留此前完整站点。

<a id="D-002"></a>
**D-002 · 凭据合同**：Token 仅在当前页面内存中；刷新、离开或主动清除后消失。只向固定 `https://api.github.com` 发送 Authorization，不记录到日志、URL、浏览器存储或构建环境。仓库配置固定在代码中，不读取或写入浏览器仓库配置。GitHub Contents 写权限本身包含修改删除能力；只新增是本应用的行为保证。

## 上传与浏览

<a id="D-003"></a>
**D-003 · 行为合同**：支持选择、拖拽、粘贴、批量上传、预览、复制 URL/Markdown，以及仓库图片列表。输入校验和图片处理在写入之前执行；内容寻址和 GitHub 新文件创建保护已有文件。完整异常与并发规则见详细设计。

```text
选择图片 → 格式/大小校验 → 预览与压缩 → 内容哈希路径
                                          │
                              查询同路径 ─┼─ 相同内容 → 复用链接
                                          ├─ 不同内容 → 拒绝覆盖
                                          └─ 不存在 → 创建文件 → 返回链接
                                                        │
                                                    失败 → 显示错误
```

上传逐张进行，每张独立报告结果；某张失败不撤销已成功图片。提交成功表示已入库，使用 GitHub 原始文件外链。图片仓库需公开且先初始化分支；私有仓库不能提供无需凭据的公开外链。

<a id="D-006"></a>
## D-006 · 多仓库透明分配

**Behavior Contract · 已授权实施**。来源：2026-09-29 用户要求“用户不必知道也不必选择”，自动分配并尽可能使各仓库存储占用接近，而非等一个仓库无法写入才报错；随后明确“旧的不用动”。轮询只是用户举例，并未指定必须采用轮询算法。

已确认：仓库选择对上传者透明，容量均衡只影响新增图片；旧图片不迁移、不修改，已有链接不变。该需求替代 D-001 中固定单仓库的约束；D-001 和详细设计 D-004 的固定单仓库部分仅描述历史实现。透明指无需用户参与分配，不承诺隐藏公开图片 URL 中的仓库名称。Token 不持久化、文章与图片分仓的既有边界保留。

采用各仓库当前图片字节总数分配，而非按图片张数轮询：每批读取完整列表，逐张处理图片；先跨仓库查找并核对相同内容，已存在则复用，否则写入当前占用最少的仓库。创建成功后按最终上传字节数更新本批统计，复用不增加占用；占用相同采用稳定顺序。图片库汇总各仓库结果，内部保留每张图片来源。

例：A/B/C 占用分别为 800/300/310 MB，新图片先进入 B；B 的成功新增使其超过 C 后，后续图片优先进入 C。新增空仓库会自然承接更多新图片，旧图片仍不移动。

现有复用点：`apps/images/src/github.ts` 的 `GitHubImages.list()` 已返回大小，`upload()` 已核对内容并拒绝覆盖；`apps/images/src/main.tsx` 已串行上传。分配与汇总仍归 images 应用；条目及链接需携带来源，不能仅替换固定配置。

边界：图片字节总数不是含历史和 Git 元数据的仓库磁盘体积，也不能证明平台剩余空间。无集中协调时，多页面同时上传只能尽量均衡，不能保证实时严格相等。读取失败或截断不能算零占用；写入超时可能已经提交，不应未经核对便换仓重复上传。

仓库池由维护者在源码配置中维护，页面不增加配置入口；用户已授权新建 hugh-image-02、hugh-image-03，与原 hugh-image 组成池；两个新仓库已创建为公开仓库并初始化 main。沿用只读连接检查与页面临时 Token，Token 需要覆盖池中全部仓库。当前仅按占用均衡，不新增容量硬阈值或自动建仓功能；异常继续显式报错，不做自动故障转移。详细合同见 [D-007](需求设计文档.md#D-007)。

模块关系：页面 → images 内部仓库池 → 既有 GitHubImages 客户端（每仓库一个）→ GitHub。仓库及图片仍是远程事实来源，池只在当前页面维护可重建的统计，不新增服务器、数据库或跨应用依赖。

```text
上传批次 → 读取所有仓库完整列表 → 逐张解码与内容标识
          读取失败：本批不写入          │
                         跨仓核对已有内容
                            ├─ 相同 → 复用原链接
                            ├─ 冲突/读取失败 → 该张失败
                            └─ 不存在 → 最少占用仓库 → 只创建
                                                     ├─ 成功：更新占用
                                                     └─ 失败：保留此前成功，报告该张失败
```

图为授权方案的批次路径；各仓库并非跨仓一致快照。写入结果未知时重试仍绑定原目标，批次后续图片重新读取占用，不回滚、不自动补写失败图片。无跨页面全局锁，两个页面同时上传同一内容可能分别落入不同仓库；每个仓库仍拒绝覆盖。

文档推演已覆盖旧图保护、新仓优先、重复内容及读写失败；独立安全审查在最终代码 diff 完成后执行。Support lenses：architecture-designer；复用已有客户端，新增池仅拥有分配和汇总。
